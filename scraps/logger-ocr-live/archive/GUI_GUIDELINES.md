# 工場作業者向けGUIの設計指針

2026-11-13作成、2026-11-17の[ヒアリング整理](HEARING_ANALYSIS.md)を反映。TkinterとPython標準ライブラリで作るGUIに向けた設計案。現在の実行コードにGUI・パス管理・推定板厚計算は含まれていない。

[本体の採用案](../SYSTEM_PLAN.md)と[現場確認票](../README.md#導入設定)を前提とする。ここでは見せ方と操作のルールを決める。実装はまだ行わない。配置・配色の細部は試作用の参考であり、本体へ機能を追加する要件にはしない。

最小構成では実測登録・比較、材料台帳、TMB自動集計を設けない。記録名は圧延依頼ごとの命名とし、入力は記録名・初期板厚・板幅とする。重大異常時は通常完了と区別して計測終了へ進める。

ロガーの収集値CSVはロガーソフトの担当とし、画面では新システムの記録・推定表示・保存状態を示す。TR100との統合画面や互換操作は設けない。新システムの取得間隔と描画間隔はそれぞれ100msを試作候補とするが、別々に実測・調整する。

圧下量計はOP／DR各1台を、カメラ1台の同じフレームから読む。側ごとのOCR状態・開き量・推定板厚を区別し、片側だけ読めないときはその側の理由を示す。もう片側はモデルに必要な入力が揃っていれば表示を続ける。計器ごとの生表示・循環解釈・時刻差は詳細で確認できるようにする。

## 1. 先に決める方針

**落ち着いた背景に、OP／DR両側の推定板厚・荷重・値を使えるか・記録状態を固定配置する。取得した点からグラフを伸ばし、次パスまでに結果を確認できる画面にする。色だけに意味を持たせない。**

「最も使いやすい配色・寸法」は、視距離、照明、手袋、入力機器、作業者によって変わる。次の区分で管理する。

| 区分 | 今回の扱い |
| --- | --- |
| この題材の基本ルール | 色と文字の併用、欠測の明示、操作位置の固定、操作対象の明記など。試作の初めから守る |
| 外部資料を参考にする基準 | コントラスト、キーボード操作、情報の階層化など。規格の要求とこの題材への採用判断を区別する |
| 現場で調整する初期値 | 文字16〜18pt、主ボタン高さ64px、画面更新100msなど。規格で義務付けられた数値ではない |
| 聞き取りから反映 | 両側板厚・荷重は必須、開始前に初期板厚・板幅を入力できる。材料単位の開始と自動パス検知を優先して検討。速度表示は優先度が低い |
| 現場確認まで保留 | 自動パス判定の条件、表示桁数、許容遅延。±0.05mm／0.1mm未満は推定誤差の目標であり製品合否には使わない |

このアプリは計測・記録・推定表示の補助に使う。GUIの「記録終了」「計測終了」は圧延機の停止ではない。圧延機の停止・非常停止・材料位置の確認を、この画面の表示で代替しない。

## 3. 配色のルール

### 基本パレット案

明るい工場内で使う初期案は、淡い灰色の背景と濃い文字にする。画面全体の緑・赤塗り、立体的な計器の装飾、常時点滅は使わない。暗所での見え方は現場で確認し、最初から複数テーマを実装しない。

| 用途 | 前景色 | 背景色 | 併記する情報 |
| --- | --- | --- | --- |
| 画面全体 | `#17212B` | `#ECEFF1` | 通常の見出し・ラベル |
| 数値・表の領域 | `#17212B` | `#FFFFFF` | 「推定板厚」「mm」など |
| 補助文字 | `#45515F` | 上記の背景 | 最終取得時刻、説明。重要情報を薄い灰色にしない |
| 操作・選択・フォーカス | `#FFFFFF` | `#1D4ED8` | 動作名、選択枠。工程の正常・異常には流用しない |
| 表示が成立している状態 | `#166534` | `#F0FDF4` | 「推定表示中」など。小さな状態表示に限定 |
| 注意・要確認 | `#7A4B00` | `#FFF4CC` | 「OCR読取不能」「基準未確認」など |
| 計測・保存の失敗 | `#B42318` | `#FEE4E2` | 「保存失敗」「取得異常で計測終了」など |
| 識別に必要な枠・グラフ線 | `#64748B` | 白または画面背景 | 入力欄の境界など。装飾の薄い罫線とは分ける |

色はこの題材の候補であり、IECの色度指定や安全標識の色を再現したものではない。既設設備と同じ意味の色になっているか、設備担当者と確認する。

- 赤は計測・記録の重大な失敗に絞る。通常の未接続、待機、記録終了を赤にしない。
- 緑は、その表示の成立条件を満たした意味に限定する。「安全」「製品合格」「OCRが正しいことの保証」を表さない。
- 黄色系の背景には濃い文字を使う。黄色の細い文字を白地に置かない。
- 色に加えて「要確認」「保存失敗」の文字と、必要なら三角形などの形を使う。赤と緑を見分けるだけのUIを作らない。
- 状態によって領域を移動・拡大しない。警告用の場所を確保し、通常の表示を押し出さない。
- 音を追加するかは、騒音・聴覚保護具・既存警報・作業手順を確認して決める。音だけでは知らせない。

[WCAGの色の使用](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)と[ISAの色の使い方の解説](https://www-prod.isa.org/web/acom/article/the-high-performance-hmi)を参考にした採用案である。

### コントラスト

通常文字は4.5:1以上、主要な文字はできるだけ7:1以上を目標にする。大きな文字も、この題材では4.5:1を下回らない方針とする。識別に必要な操作部品の境界、状態表示、グラフ線は隣接色と3:1以上を目安とする。[文字の基準](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)・[非テキストの基準](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

候補色のsRGB値から計算した比は、本文／白16.29:1、本文／画面背景14.11:1、補助文字／画面背景7.01:1、白文字／青6.70:1、緑の組6.81:1、注意の組6.73:1、失敗の組5.45:1、枠／画面背景4.12:1。表示した比は丸め値であり、閾値の判定には丸め前の値を使う。

これは指定色の計算結果であり、反射・汚れ・アンチエイリアス・テーマによる実際の見え方の検証結果ではない。通常・押下・選択・フォーカス時も確認する。無効なボタンは別の外観にし、無効理由を読みやすい文字で近くに示す。

## 4. 文字・寸法・余白の初期値

次は、マウス操作、視距離おおむね50〜80cmを仮定した試作値。pxは100%表示時の設計上の基準で、Tkinterの実際のpxやWebのCSS pxと常に一致する単位ではない。

| 要素 | 初期値 | 調整時に確認すること |
| --- | --- | --- |
| 基本文字・ボタン文字 | 16〜18pt | 姿勢を前に倒さず読めるか |
| 状態・現在パス | 20〜24pt | 数値の有効性と対象を短い視線移動で確認できるか |
| 現在の推定板厚 | 56〜72pt、太字 | 視距離、最大桁数、小数点・負号、警告時の幅 |
| 単位 | 20〜24pt | 数値の隣に常時表示し、値の変化で位置を動かさない |
| 履歴・グラフ目盛 | 14〜16pt | 件数を増やすために文字を小さくしない |
| 主操作ボタン | 高さ64px、幅200px以上 | 文字が収まり、押せる領域全体が有効か |
| 補助操作ボタン | 高さ48px以上、文字幅に応じた幅 | 小さなアイコンだけにしない |
| ボタン間 | 16px以上 | 隣の操作を誤って押さないか |
| 記録操作と計測終了の間 | 32px以上 | 材料の記録終了とアプリ全体の終了を混同しないか |
| 領域内の余白／領域間 | 16px／24pxを基本 | 状態文が2行になっても重ならないか |
| 履歴の行高 | 40〜48px | 行選択する運用なら、実機で押しやすさを再確認 |

厚労省の指針には、文字の高さはおおむね3mm以上が望ましいこと、視距離はおおむね40cm以上を確保することが示されている。これは遠方から見る工場画面の十分条件ではない。ptは文字そのものの実測高さとも一致しないため、実際の画面を定規で測り、作業位置から確認する。[厚労省のガイドライン](https://www.mhlw.go.jp/web/t_doc?dataId=00tc6314&dataType=1&pageNo=1)

WCAG 2.2の操作対象は、AAの最小基準が原則24×24 CSS px、AAAの拡張基準が原則44×44 CSS pxで、いずれも例外がある。この小ささを工場での設計目標にせず、大きい側から試す。手袋・立位・タッチ操作を使う場合は、主ボタン高さ72〜88pxなどを比較し、実際の手袋と画面で判断する。大きくしても、手袋非対応のタッチパネルでは入力できない。[最小サイズ](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)・[拡張サイズ](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)

フォントは運用PCにある読みやすい日本語ゴシック体を使う。まずメイリオなどを実機で比較し、UD書体は既に利用可能なら候補にする。UDという名称だけで採用せず、0・6・8・9、小数点、負号、似た日本語を見分けられるかで選ぶ。専用フォントや7セグ風フォントは追加しない。

## 5. 通常画面の配置

画面を開いたときに「どの材料・パスか」「推定値を使えるか」「記録しているか」を確認できる配置にする。

```text
┌─────────────────────────────────────────────────────┐
│ 記録名：圧延依頼の名前       パス：03    詳細・設定   │
├─────────────────────────────────────────────────────┤
│ 表示状態：推定表示中        記録：記録中          │
│ 警告・理由・次の行動のための固定領域                  │
├───────────────────────────────┬─────────────────────┤
│ 推定板厚 OP／DR               │ パス履歴            │
│       1.234 ／ 1.245 mm        │ 番号・両側の結果    │
│ 荷重 OP／DR  50.0／51.0 ton    │ 有効数・確認理由    │
│ 推定・暫定式／入力から0.2秒    │                     │
├───────────────────────────────┤                     │
│ 現在パスのOP／DR板厚推移      │                     │
│ 縦軸：板厚mm                  │                     │
│ 共通の横軸：パスの経過時間    │                     │
├───────────────────────────────┴─────────────────────┤
│ [記録開始] [記録終了]           [計測終了]    │
│ 基準：確認済み             保存：処理側で確認した状態 │
└─────────────────────────────────────────────────────┘
```

数値、識別子、桁数、荷重単位は配置検討用の仮例。実値の算出・精度検証済みを意味しない。最小構成の履歴はパス番号・開始終了・状態を示し、代表厚さやTMBの集計値は追加しない。「推定」「暫定式」を外さず、表示桁数が測定精度を保証すると受け取られないようにする。両側数値を置いたときの文字サイズ・配置は実寸で評価する。

開始前の準備では、依頼ごとの記録名・初期板厚mm・板幅mmを入力し、係数C1〜C5とゼロ基準P0を確認する。初期板厚は開始条件の記録、板幅はkbの計算に使う。記録開始と機械の圧延開始は別の操作とし、毎パスの開始・終了ボタンは通常画面の必須操作にしない。

- 左側おおむね2/3を現在値と推移、右側おおむね1/3を履歴に使う案から始める。
- 対象識別、表示状態、両側板厚・両側荷重、記録状態、主操作を同じ通常画面に残す。通常操作で画面全体をスクロールさせない。
- 履歴が収まらなければ履歴だけスクロールする。作業者が過去行を見ている間に、自動更新で選択やスクロール位置を奪わない。
- 通常は「記録中」、履歴は「記録完了／要確認／中断」を明示する。入力が有効なことと保存成功を同じ表示にまとめない。
- 接続・基準確認・材料条件入力は準備時に見せる。通常の記録操作と、校正座標・換算点・係数の編集を同じ操作列に置かない。
- 詳細画面にはOCR値、CHごとの状態、入力ごとの古さ、時刻差、設定を置く。主な欠測理由は詳細を開かなくても分かるようにする。
- 実効作業領域1280×720程度を仮基準にする。物理解像度だけで対応可否を決めず、Windowsの拡大率・タイトルバー・タスクバーを含めた残り領域を確認する。
- 幅が足りない場合は履歴を別表示にするなど、情報の優先度で調整する。文字・主ボタンを縮小して詰め込まない。

推移は1点目を点として示し、以後は取得に応じて伸ばす。経過時間を横軸にし、材料上の位置とは呼ばない。板厚のOP／DRは共通の縦軸範囲で比べ、線種・凡例でも識別する。荷重は通常画面の数値で示し、荷重グラフは初期機能に追加しない。欠測区間を線でつながず、平滑化や補間で読取不能を隠さない。縦軸はパス中に頻繁に変えず、範囲外になったことを示す。

パス終了前は終端未確定とし、抜け判定後に結果を閉じる。最小構成では絶対板厚mmを経過時間の軸で表示し、TMB自動集計・目標偏差・合否色は追加しない。速度は通常画面の必須表示に含めない。

## 6. 表示状態と数値の扱い

工程の状態、入力の品質、記録・保存の状態は別に持ち、画面上で並べて示す。例えば「圧延中／OCR読取不能／記録継続・要確認」が同時に成立し得る。欠測時に記録を続ける条件は追加確認で決める。

| 状況 | 現在値欄 | 状態・色の例 | 作業者へ伝えること |
| --- | --- | --- | --- |
| 未接続・接続待ち | `— mm` | 中立色・「未接続」「接続中」 | まだ値を取得していない |
| 接続済み、基準未確認 | `— mm` | 注意・「基準未確認」 | 基準確認が必要。毎回ゼロ調をやり直す意味ではない |
| 材料待ち・計算対象外 | `— mm` | 中立色・「材料待ち」 | 直前パスの結果は履歴へ置く |
| 左右モデル未確認・開き量の循環解釈が不明 | 該当側は`— mm` | 注意・「未算出」「ギャップ解釈未確認」 | 荷重や生OCRが読めていても、板厚の有効性は別 |
| 必要入力・基準・計算条件が成立 | 推定値と単位 | 小さな緑表示・「推定表示中」 | 実測値・合否・機械の安全確認とは区別する |
| OCR読取不能・必要CH欠測 | `— mm` | 注意・理由を明記 | 現在値がない。最後の値を大きな欄に残さない |
| 入力の古さ・時刻差が許容外 | `— mm` | 注意・「OCR更新停止」「入力時刻差超過」 | どの入力が、どれだけ遅れているか |
| 取得異常で終了 | `— mm` | 失敗・「取得異常で計測終了」 | 失敗した入力、次に確認する箇所 |
| 保存失敗 | 有効性に従う。表示継続の可否は運用で決める | 失敗・「保存失敗」 | 保存先と対処。正常なパス完了にしない |
| 終了処理中 | `— mm` | 中立色・「ロガー終了確認中」 | 計測を終了処理中であること |
| 終了確認が取れない | `— mm` | 失敗・「ロガー停止未確認」 | プロセス終了だけで機器停止済みとしない |

0.000は有効なゼロであり、欠測の代わりに使わない。過去の有効値を参照する必要があれば、小さな別欄に「前回有効値・取得時刻」と明記する。処理側が止まった場合も、GUIが独立して最終入力・最終処理時刻を確認して表示を無効にする。GUI自身のフリーズをGUI内だけで通知できるとは考えない。

両側板厚・荷重は項目ごとの有効性を持つ。算出できないDR板厚をOP板厚で埋めず、片側欠測で他の有効な観測値まで隠さない。板厚に両側入力が必要なモデルなら、その依存関係に従って無効化する。片側を算出できない試作を、両側表示の必須要件を満たしたとはしない。

現在の`MAX_TIME_GAP = 0.15`秒、`INPUT_TIMEOUT = 1`秒、`FAILURE_TIMEOUT = 15`秒は既存の検証用設定であり、作業に許容される遅延を証明した値ではない。読取不能と受信停止も区別する。15秒の異常打切りまで古い数値を表示し続ける設計にはしない。

画面を描き直した時刻を入力の取得時刻として使わない。同じ数値が届き続けていることと、更新が途絶えたことを区別する。古さには単調増加時計を使い、グラフ・現在値・状態を同じ表示データから更新する。

通常画面で入力の古さを1つにまとめる場合は、推定に必要な入力のうち最も古いものを示す。詳細では入力ごとの古さを示し、新しい片側の受信で古いもう片側を隠さない。

## 7. 操作と誤操作防止

- 「開始」「停止」「リセット」だけのラベルを避け、「記録開始」「記録終了」「計測終了」「基準確認」と対象を明記する。
- 開始と終了は別ボタンで常に同じ位置に置く。開始操作の直後に同じ場所を終了操作へ切り替える方式は、連打による誤操作を避けるため初期案にしない。
- 実行できない操作は無効にする。例：記録中は再開始不可、終了処理中は再接続不可。押せない理由は近くの文字で示す。
- ボタンを押したら「開始要求中」などの応答を返し、処理側の受理を受けて記録中にする。パス番号は処理側の判定結果で更新する。処理側でも重複・不正な状態からの要求を拒否する。
- 一般操作は1回のクリック・タップで行う。ダブルクリック、ドラッグ、右クリック、ホバーだけに依存する操作を必須にしない。
- Tab／Shift+Tabで自然な順序に移動し、フォーカスを見えるようにする。フォーカス中の標準ボタンをキーボードでも操作できるようにする。
- Enterを画面全体の記録開始・終了に割り当てない。入力欄での確定や日本語変換と衝突させない。ショートカットは現場で必要性を確認し、追加するならボタン上にも示す。
- 通知で入力中のフォーカスを奪わない。読取不能が1フレーム出るたびにダイアログを開かない。
- 通常の記録開始に毎回の確認ダイアログを追加しない。圧延中の記録終了、計測終了や基準の置換など、影響が大きい操作だけ具体的に確認する。
- 終了確認は「パス03の記録を中断して計測を終了します」など、結果を明記する。「はい／いいえ」だけにせず、実行内容と「戻る」を示し、戻る側を既定にする。
- ウィンドウの×も計測終了と同じ経路にする。終了確認・保存結果を待ち、失敗を通常完了として閉じない。
- 圧延中は材料の変更、基準の置換、係数の適用を行わせない。パス間の板幅更新の要否は追加確認で決める。編集値は確定前に検証し、異常箇所・単位・許容範囲を短く示す。入力を黙って補正しない。

警告は「原因→影響→次の確認」の順に短く書く。例：「OCR更新停止：1.2秒受信なし。推定板厚を表示できません。カメラ接続を確認してください」。解消したら現在の警告を解除するが、そのパスが欠測を含んだ記録は残す。同じ原因の警告を何件も積み重ねない。

## 8. Tkinterで実装するときの方針

### 標準の部品を使う

`tkinter`、`tkinter.ttk`、`tkinter.font`を使う。追加のGUIライブラリ、テーマライブラリ、グラフライブラリは入れない。既存の画像取得・計算用依存関係は、その用途で引き続き使う。

実装前に、運用するPython環境で`uv run python -m tkinter`を実行し、Tkの確認用ウィンドウが開くかとTcl/Tkの版を確認する。標準ライブラリでも、Pythonの配布環境によって利用可否が変わり得るため、未確認のまま利用可能とは判断しない。[Tkinterの公式文書](https://docs.python.org/3.13/library/tkinter.html)

| 用途 | 最初に使う部品・方法 |
| --- | --- |
| 画面の区画 | `ttk.Frame`と`grid()`、行列の`weight`、`sticky` |
| 現在値・状態 | `ttk.Label`、`StringVar`、`tkinter.font.Font` |
| 操作 | `ttk.Button`。独自Canvasボタンを作らない |
| 入力 | `ttk.Entry`、候補固定なら`ttk.Combobox(state="readonly")` |
| パス履歴 | `ttk.Treeview`と`ttk.Scrollbar`。色だけでなく状態列も持つ |
| 厚さ推移 | `tkinter.Canvas`で線・軸・目盛を描く。点数を表示幅に合わせて抑えるが、欠測境界を消さない |
| 詳細・設定 | 必要なときに`Toplevel`。`Tk()`は1つにする |
| 定期描画・終了状況の確認 | `after()`。機器処理・長い待機をイベント処理内に置かない |

初期の`main.py`に設定、状態、画面構築、短い操作受付、表示更新を置き、既存の取得子を使うB案に沿わせる。関数名は役割が分かるものにし、汎用GUIフレームワークや継承階層を先に作らない。

### 見た目と拡大率

色・フォント・余白を先頭の少数の定数にまとめ、`ttk.Style.configure()`と`map()`で通常・無効・押下・選択・フォーカスの外観を確認する。Windowsネイティブテーマでは、指定色が期待どおり反映されない部品があるため、テーマ名だけで成立と判断しない。

まず標準テーマで読みやすさとキーボード操作を確認し、色の統一が難しければ同梱の`clam`も比較する。状態色はラベル・警告領域に持たせ、ボタンの塗りだけに処理の状態を依存させない。[ttkとStyleの公式文書](https://docs.python.org/3.13/library/tkinter.ttk.html)

フォントの正のsizeはpt、負のsizeはpxである。`Font.measure()`で最大表示文字列の幅を測り、`metrics()`で行高を確認する。`ttk.Button(width=...)`を画素幅だと思って指定せず、フォント・padding・配置後の実寸を見て調整する。[Fontの公式文書](https://docs.python.org/3.13/library/tkinter.font.html)

Tkの`tk scaling`は「1pt当たりのpx」であり、Windowsの125%という値をそのまま1.25として設定するものではない。起動時の値を尊重して実機確認し、必要が分かった場合に限って補正する。文字だけを拡大して、余白・行高・操作領域が取り残されないようにする。[Tkのscalingの定義](https://www.tcl-lang.org/man/tcl8.6/TkCmd/tk.htm)

Windowsの100%・125%・150%、使用予定の拡大率が別ならその倍率でも確認する。複数画面を使う場合は画面間移動も確認する。小さすぎる作業領域を固定の`minsize`で画面外へはみ出させず、対象端末で成立するレイアウトを決める。

### 描画と取得を分ける

Tkinterのウィジェットと`StringVar`の更新はGUIメインスレッドに集める。取得子・処理側とのデータの渡し方は[既存設計の5章](DESIGN.md#5-案bでの処理フロー)に従う。表示更新は`after(100, ...)`を初期候補にし、必要なら50msと比較する。これは描画間隔の要求であり、入力から表示まで100ms以内という保証ではない。[Tkinterのイベント処理とスレッド](https://docs.python.org/3.13/library/tkinter.html#threading-model)

現在値の描画は最新の表示データへ追い付くようにし、古い描画を全部再生しない。パス確定・エラー・操作結果は順序を保って受け取る。COM、SDK、ファイル書込み、`sleep()`、長い`wait()`や`join()`をボタンのコールバックへ直接移さない。

標準ウィジェットを使うだけで、スクリーンリーダーやWindowsのコントラストテーマへの対応が保証されるとはしない。実際に必要な支援機能がある場合は早い試作段階で運用PCと一緒に確認し、Tkinterで満たせるか判断する。Canvas上のグラフだけに重要な状態を置かず、テキスト・履歴にも同じ要点を残す。

## 9. 実装までの進め方

1. **現場条件を記録する。** モニターの型・サイズ・解像度・拡大率、実作業での視距離・姿勢、照明・反射、手袋、入力機器、既設盤の色と用語を確認する。ベテランと初めて使う作業者の両方に、板厚を見る場面と操作の余裕を聞く。
2. **実寸の配置案を見てもらう。** 事前入力、両側数値・推移、材料待ち、未算出、読取不能、更新停止、保存失敗、終了確認中を比較する。依頼ごとの記録操作と自動パス検知を中心に、記録名・両側表示・欠測状態を確認する。
3. **標準Tkinterだけで模擬表示を作る。** 実機には接続せず、上記の状態、最大桁数、長い識別名、ゼロ・負号を切り替える。配色・文字・余白は定数を直して比較し、調整画面やテーマ切替機能は先に作らない。
4. **表示と操作のルールを確認する。** 実寸・拡大率・キーボード・連打・×・警告時のレイアウトを調べる。支援機能の要件があればこの段階で確認する。
5. **取得・計算・記録へ接続する。** B案の現在値・履歴・操作要求を接続する。入力の断線、古い入力、処理停止、保存失敗、終了確認失敗を模擬する。
6. **現場で測って決定する。** いつもの姿勢・照明・手袋で操作してもらい、読み間違い、誤クリック、押し忘れ、判断までの時間と表示遅延を記録する。表示精度の評価は、操作性の評価と分けて行う。

## 10. 試作の確認項目

以下の秒数・操作目標は、この題材の評価用仮値。規格の合格基準ではなく、現場の作業時間と合わせて決め直す。

| 確認 | 仮の到達目標・記録内容 |
| --- | --- |
| 一目で読めるか | 通常の姿勢で2秒程度の一瞥から、OP／DRの推定板厚・荷重・単位・対象パスを取り違えず読めるかを評価する |
| 無効値を見分けられるか | 読取不能・更新停止の画面を有効な現在値と取り違えない。5秒程度で理由と次の確認を説明できる |
| 色だけに依存していないか | グレースケールでも表示状態・記録状態・確認理由が分かる。色覚シミュレーションだけで評価を終えない |
| 操作対象を間違えないか | 記録終了と計測終了、機械の停止を取り違えない。試行中の混同は修正対象にする |
| 誤クリック・連打 | 実際の入力機器・手袋で隣のボタンを誤って実行しない。連打でもパスが重複しない |
| 操作に反応するか | 受付中の表示は押下後おおむね200ms以内を仮目標にし、機器の処理完了とは分けて測る |
| 値の見せ方 | 0.000と欠測、推定と計算不能、現在値と前回値、記録中と記録完了が区別できる |
| 異常・復帰・終了 | 断線・処理停止・保存失敗・終了失敗で状態が変わる。復帰後も欠測があった履歴を失わない |
| サイズ・拡大 | 対象端末の倍率で、長いラベルや最大桁数が欠けず、主操作が画面内にある |
| キーボード・フォーカス | マウスなしで必要操作に到達できる。通知で入力・選択を奪われない |
| 長時間運転 | 履歴増加で画面が遅れない。入力から画面までの遅延の中央値・95パーセンタイル・最大値を記録 |
| 次パス前の確認 | 1点目から表示され、先端尾端・両側差を確認できる。パス終了と保存がいつ終わるかを次パス準備時間と比べる |

評価記録には、作業者の経験、端末・倍率、視距離、照明、手袋・入力機器、試した操作、読み違い・押し間違い、修正内容を残す。少人数の試行で問題がなかったことを、全利用者での使いやすさの保証とはしない。
