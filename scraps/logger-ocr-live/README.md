# ロガー電圧と圧下量表示の取得・照合

Windows PCでNR-600の現在電圧と、計器を撮影した画像のOCR値を取得する題材です。

## 実装状況

本体の現行コードは、1表示のOCR、電圧の2点換算、時刻照合と標準出力CSVまでです。本体へのOP／DRの2表示OCR、リアルタイムの板厚計算、パス判定、GUI、依頼ごとのファイル保存の組込みは未実装です。手入力した実測データから係数を求める[単体スクリプト](#手入力の測定値から係数を求める)もあります。

[OCR比較試作](sandbox/ocr-comparison/README.md)は本体から独立し、静止画像によるOP／DR各42点の校正と、同じ保存画像での固定二値化・適応二値化・Bayer赤画素判定を試せます。校正はPNGに限らずOpenCVで読める画像を使い、Qt版OpenCVの標準機能でホイール拡大・ドラッグ移動できます。WindowsのQt試験用環境はsandboxの手順で別途作成します。カメラSDKが必要なのは撮影時だけです。本体の採用方式と1表示用の校正手順は、以下のままです。

| 計器・撮影 | MDR-060MをOP／DR各1台、BG505LMCFカメラ1台で同じ画像へ撮る | 構成確定 |

| カメラ温度 | 追加放熱機構を付けない想定で、本番の取付具・給電・撮影条件を使い、連続撮影時と撮影停止後の待機時の周囲温度・筐体上面温度を測る。使用範囲は周囲0〜40℃、筐体上面60℃以下 | 現場で温度の余裕を確認。[製品仕様](https://www.toshiba-teli.co.jp/products/industrial-camera/gige-camera-bg505lm.htm)・[熱設計ガイドライン](https://www.toshiba-teli.co.jp/technology/technical/t0001_ThermalDesign.htm) |

| ゼロ基準 | ロール交換時の各50トンの平行出しと、各7トンのゼロ設定を区別。実際のP0_OP・P0_DR、ロールと基準の対応を記録 | 具体値を指定 |

| 新システムの保存先 | リポジトリ外の書込可能なローカルフォルダ | 導入時に指定 |

メーカー仕様でMDR-060Mは6桁、計数範囲0〜999999、メモリ付きです。メモリ機能だけで機械側の基準の継続まで保証せず、実際の機器設定と運転状態を確認します。[製品仕様](https://www.line.co.jp/product/1783/)、[取扱説明書](https://www.line.co.jp/wp-content/uploads/2023/02/MDR0X0MmanualJ.pdf)

実験でC1〜C5と適用範囲を求め、実際の荷重列でパスの開始・終了閾値を確認します。係数の尺度は基準幅でkb＝1とし、板厚式のPとP0には同じ入力板幅のkbを使います。取得周期、OCR・表示の遅延、パス判定と板厚の精度は[初版の検証手順](SYSTEM_PLAN.md#9-検証と導入)に沿って実測します。

## 実行環境

Windows x64とPython 3.13を使います。pytelicam 1.1.1の対応Pythonは3.9～3.13のため、この題材は3.13に固定しています。以下のコマンドはすべて `scraps/logger-ocr-live` で実行します。

```powershell
uv python install 3.13
uv sync --inexact
uv run python --version
```

Webカメラ・動画・東芝テリー・ロガーで同じ `.venv` を使います。東芝テリー用のpytelicamはメーカー配布wheelを別途導入します。導入後も保持するため、依存関係の同期には `uv sync --inexact` を使います。`uv run` も追加導入したパッケージを保持します。

## 手入力の測定値から係数を求める

試行用のフォルダをリポジトリ外に作り、測定CSVを置きます。ロガーやカメラを接続せずに実行できます。

1. `measurements.csv` に、同じ側・位置で対応する板幅、片側荷重、ロール開き量、出側実測板厚を記入します。表計算ソフトから保存する場合はCSV UTF-8を選びます。下記のヘッダーと列順を使い、小数点は `.`、長さの単位はmmとします。

   ```csv
   side,width_mm,load,gap_mm,measured_thickness_mm
   ```

2. `src/fit_mill_model.py` 冒頭で入出力先と実験条件を設定します。例の値を手元の記録に置き換え、測定した側の条件を `op` または `dr` に記入します。基準幅にはその側の測定データの最大板幅を指定し、同じ幅の点では `width_mm` を揃えます。相対パスはコマンドを実行するフォルダが基準です。

   ```python
   MEASUREMENTS_FILE = Path(r"C:\measurement\trial-01\measurements.csv")
   OUTPUT_ROOT = Path(r"C:\measurement\trial-01")
   CONDITIONS = {
       "roll": "試験ロールA",
       "zero_reference": "試験時のゼロ設定A",
       "load_unit": "ton",
       "op": {"p0": 7.0, "reference_width_mm": 1000.0},
   }
   ```

3. 引数なしで実行します。

   ```powershell
   uv run python src/fit_mill_model.py
   ```

側ごとの係数、板厚の評価件数、平均誤差と最大絶対誤差がターミナルに出ます。実行ごとに `OUTPUT_ROOT` に `fit-日時` フォルダを作り、条件と係数を `coefficients.json`、各点の予測と誤差を `comparison.csv` に保存します。使う測定点を変えたら、同じコマンドで再計算できます。

基準幅だけでも、異なる荷重の点が揃っていればC1・C2を求められます。C3〜C5には、基準幅を含む3種類以上の板幅と、幅ごとに異なる荷重での測定が必要です。出力の誤差は係数を求めるのに使った点での値です。計算式と入力条件は[係数特定要件](COEFFICIENT_FIT.md)を参照してください。

## 設定と実行

1. 使用するユニットの電圧CH（初期設定ではユニット1のCH1〜8）を有効にし、入力レンジを±10Vにして、連続収集用の `.ucf` を作ります。WAVE LOGGER PROを終了し、`src/logger.py` の `SETTINGS_FILE` にそのパスを、`DEVICE_ID` に本体IDを設定します。連続収集・対象CH・入力レンジはWAVE LOGGER PRO側で設定します。
2. OCRを校正し、表示された5項目を `src` の `counter.py` に貼り付け、入力を選びます。初期の点は既存の合成動画用です。MDR-060Mの赤い6桁7セグを整数として読み、1000で割って `0.000`〜`999.999` として扱います。計器そのものに小数点はありません。[入力の切り替え](#ocrの入力を切り替える)・[OCRの校正手順](#ocrを校正する)
3. `src/main.py` の `CHANNELS` に取得・換算するCHを設定します。現在はCH1・2・3・6・7の5CHが有効で、CH4・5・8はコメントアウトしています。対応候補は下表のとおりです。実配線に合わせて名称・単位・2点の換算値を確認し、使用するキーだけを有効にします。現在の設定値を実機で校正済みとは扱わないでください。換算点が未設定・不正なら取得を開始しません。計算側がCH名を取得側に渡すため、取得側でCHを重ねて設定する必要はありません。

| CH | 初期の名称 | 信号 |
| --- | --- | --- |
| `U1_CH1` | `rolling_speed` | 圧延速度 |
| `U1_CH2` | `load_OP` | 圧延荷重OP |
| `U1_CH3` | `load_DR` | 圧延荷重DR |
| `U1_CH4` | `tension_in` | 入側張力 |
| `U1_CH5` | `tension_out` | 出側張力 |
| `U1_CH6` | `bender_Inc` | ベンダーInc |
| `U1_CH7` | `bender_Dec` | ベンダーDec |
| `U1_CH8` | `exit_thickness` | 出側板厚 |

`U1_CH1` はユニット1の電圧CH1です。例えばCH2が1～3Vで0～100tonを表す場合、その設定欄は次のようになります。説明用の仮値なので、実際の単位・対応値に置き換えます。

```python
"U1_CH2": {
    "name": "load_OP",
    "unit": "ton",
    "low_point": (1.0, 0.0),
    "high_point": (3.0, 100.0),
},
```

`low_point` と `high_point` はそれぞれ `(電圧, 換算後の値)` です。電圧は−10～10V内で、低い点から順に指定します。換算後の値は増加・減少のどちらでも構いません。基準2点の電圧範囲をそのまま有効範囲にし、端点を含めて換算します。範囲外は外挿せず、換算値を欠測にします。以前の `valid_voltage` は不要です。

ロガーの測定レンジ±10Vと、信号ごとの換算範囲は別です。0～8V、1～3VなどをCHごとに設定できます。例えば `(0.0, 0.0)` と `(8.0, 80.0)` なら4Vは40になります。`unit` は換算後の数値に付ける表記で、mpm・ton・kgなどをCHごとに指定できます。単位同士の自動変換やCH間の加減算は行いません。±10Vの実際の入力レンジは `.ucf` 側で設定します。

`Ctrl+C` または片方の取得終了で両方の取得を停止します。長時間の無更新や受信処理の失敗でも両方を停止し、自動再起動はしません。終了後はWAVE LOGGER PROの画面で収集停止を確認してください。[無更新・異常・終了の扱い](#無更新異常終了の扱い)

```powershell
uv run python src/main.py
```

## 単体で確認する

ロガー取得とOCR取得はそれぞれ単体で動きます。以下は `scraps/logger-ocr-live` を開いた状態で実行します。単体起動では `--managed` を付けません。終了は `Ctrl+C` です。

### OCRの入力を切り替える

`src/counter.py` 先頭の `SOURCE = None` を、使う入力に対応する下表の設定例に置き換えます。

| 入力 | 設定例 | 実行環境 |
| --- | --- | --- |
| Webカメラ | `SOURCE = 0` | 通常の `.venv` |
| 動画 | `SOURCE = r"C:\measurement\recorded.avi"` | 通常の `.venv` |
| 東芝テリー | `SOURCE = ("teli", 0)` | 同じ `.venv` にpytelicamを追加、TeliCamSDKが必要 |

東芝テリーの番号はTeliCamSDKの検出順で、1台なら番号 `0` です。入力や撮影解像度を変えたら、その条件で校正します。

#### 東芝テリーを使う場合

TeliCamSDK（64bit）と使用するカメラのドライバをメーカーの手順に沿ってインストールします。ダウンロードした `pytelicam_v1_1_1_win64` はPython用ライブラリ・マニュアル・サンプルの配布物です。

次に、同じ `.venv` にPython 3.13用のwheelを導入します。配布物の展開先が異なる場合はパスを変更します。

```powershell
uv pip install --python .venv\Scripts\python.exe "hoge\wheel_files\pytelicam-1.1.1-cp313-cp313-win_amd64.whl"
uv run python -c "import pytelicam; print(pytelicam.__version__)"
```

校正にはライブ取得と同じ解像度・向きのPNGを使います。`src` の `camera_calibration.py` の `SOURCE` にPNGのパスを設定して校正し、表示された設定を `counter.py` に貼り付け、`SOURCE = ("teli", 0)` に変更します。

`camera_sdk.py` は開始前にトリガーモードをOFFにし、最新の受信画像をBGR24に変換します。モノクロ画像は受け付けません。解像度や露光はカメラ側で設定し、校正条件と合わせます。画像が1秒間届かなければ取得をエラー終了します。

### OCRを校正する

`src` の `camera_calibration.py` を使います。先頭の `SOURCE` にWebカメラの番号、動画のパス、または校正用PNGのパスを指定します。`REFLECTION` は `none`（補正なし）、`horizontal`（左右反転）、`vertical`（上下反転）、`both`（両方）から選び、既知の数字が正しく見えることを確認します。

```powershell
uv run python src/camera_calibration.py
```

`SAMPLE_RADIUS = 1`、`SAMPLE_LENGTH_RADIUS = None` は各点の周囲3×3画素を読みます。`SAMPLE_LENGTH_RADIUS` を `4` にすると、同じ半径1で横線は横長9×3、縦線は縦長3×9になります。線の一部がぼやける場合に試し、プレビューで帯が線の内側に収まり、隣の線や反射を含まない位置を選びます。半径は元の撮影画像上の画素数です。

カメラと計器を固定し、ピントや露光を調整します。全桁が `8` の表示テストなど、消灯部を含む全セグメントの位置が分かる画像を使ってください。

`Space` で画像を止め、左の桁から、各桁の上→右上→右下→下→左下→左上→中央の順に、点灯時に白飛びしない赤い箇所を左クリックします。計42クリックです。`B` で直前の点を取り消せます。42点が揃ったら `Enter` で確定し、出力した `FRAME_SIZE`、`REFLECTION`、`SAMPLE_RADIUS`、`SAMPLE_LENGTH_RADIUS`、`SEGMENT_POINTS` を `src` の `counter.py` に貼り付けます。

動画では停止前に `N` で次のフレームへ進めます。中止は `Q`、`Esc`、画面の×です。中止した場合は設定を出力しません。画像端から読み取り範囲がはみ出す点は受け付けず、同じ部位を選び直します。縮小表示でも点と半径は元の撮影画像の座標です。カメラを動かしたときや解像度を変えたときも再校正します。校正スクリプトは単独で動き、設定値を表示するだけで読み取り側のファイルは書き換えません。

`--json`を付けると、同じ5項目をJSONとして標準出力に出します。試作のBGR・Bayer判定で同じ校正設定を共有するときに使います。

既定では領域内の赤い画素率で点灯・消灯を判定します。読み取り時は校正座標を元画像の向きに変換し、必要な画素だけを抽出します。判定が曖昧な場合や、白い画素率が `OFF_FRACTION`（初期値0.15）を超える場合は、そのフレームの値を `null` にします。

`STABLE_FRAMES`の初期値は1で、読めたフレームを直ちに出力します。先頭の消灯はゼロサプレスとして許容し、`    12`は`0.012`になります。全桁消灯や途中・末尾の空白は欠測です。`STABLE_FRAMES`を2以上に設定した場合は、従来どおり同じ値の連続一致を待ち、読取不能で連続回数をリセットします。

#### 明るい場所で点灯の赤みが弱い場合

`--segment-scores` を付けると、領域ごとの `R - max(G, B)` の中央値と、白い画素が多い領域の番号を標準エラーに表示します。数字は校正時と同じ順で、左端の桁の上が1番です。標準出力のJSONLとは別に記録できます。

### OCRだけ取得する

OCRだけを動かす場合は、校正した設定と `SOURCE` を指定して次を実行します。ロガーや換算の設定は不要です。

```powershell
uv run python src/counter.py
uv run python src/counter.py --segment-scores
```

標準出力に `received_at`・`acquired_mono_ns`・`value` のJSONLが出ます。未確定・読取不能は `null` です。読み取り位置は校正画面で、赤みと白い画素は `--segment-scores` で確認できます。

### ロガーだけ取得する

ロガーだけを動かす場合は、`src/logger.py` 冒頭の `SETTINGS_FILE` に実機の `.ucf`、`DEVICE_ID` に本体ID、`UNIT_NUMBER` に取得対象の入力ユニット番号（初期値 `1`）を設定します。`CHANNEL_NUMBERS` は単体起動で取得するCH番号の一覧です。現在は `[1, 2, 3, 6, 7]` で、例えばCH1・CH3・CH5だけなら `[1, 3, 5]` とします。引数なしで実行すると、この設定に従います。OCRや `src/main.py` の設定は不要です。

`UNIT_NUMBER` を変更する場合は、`.ucf` のユニット構成とCHの設定を確認してください。`src/main.py` と連携するときは、`src/main.py` の `CHANNELS` のキー（例：`U2_CH1`）も同じユニット番号に揃える必要があります。

その実行だけ取得するCHを変える場合は、従来どおり引数で `U1_CH3` などのCH名を指定できます（ユニット番号は設定に合わせます）。引数のCH名を `CHANNEL_NUMBERS` より優先します。連携起動時は `src/main.py` の `CHANNELS` のキーからCH名を渡すため、`CHANNEL_NUMBERS` は参照しません。

```powershell
uv run python src/logger.py
uv run python src/logger.py U1_CH1 U1_CH8
```

標準出力に `received_at`・`acquired_mono_ns`・取得CHの `voltages` のJSONLが出ます。出力は換算前の電圧で、無効値は `null` です。終了は `Ctrl+C` です。終了後はWAVE LOGGER PROの画面で収集停止を確認します。連携起動では `CHANNEL_NUMBERS` の変更は不要ですが、`UNIT_NUMBER` は `src/main.py` のCH名と一致させてください。

`src/main.py` は両方の取得を起動して、電圧の換算とOCR値の時刻照合を行います。片方だけで換算・照合する起動方法はありません。

## 出力と時刻の照合

- ロガーは `received_at`・`acquired_mono_ns` と、CH名ごとの `voltages` を出力します。ロガーの無効値は `null` です。
- OCRは `received_at`・`acquired_mono_ns`・`value` を出力します。未確定の `value` は `null` です。
- 照合結果は標準出力のCSVに出ます。ロガーの新しい行ごとに、生電圧、換算値、最新のOCR値、時刻差、`voltage_status`、`ocr_status` を表示します。範囲外の生電圧はCSVに残り、対応する換算欄は空欄になります。他の有効なCHはそのまま換算します。記録する場合は標準出力を新しいCSVファイルにリダイレクトします。

`voltage_status` は `valid`（設定した全CHを換算できた）または `invalid`（いずれかのCHが欠測・範囲外）です。`ocr_status` は `ready`（OCR値が確定し、時刻差が上限以内）、`waiting`（OCR待ち、または受信停止）、`unreadable`（OCR未確定）、`time_gap`（時刻差が上限を超過）のいずれかです。電圧とOCRの状態は独立しており、照合に使えるのは `valid` かつ `ready` の行です。以前の `status` 列はこの2列に置き換えました。片側の受信が途切れたときは、`INPUT_TIMEOUT` 秒後にコンソールへ欠測を通知します。

時刻差は両方の `received_at` の絶対差です。ロガーは指定CHを読み終えたPC時刻、OCRはPCがフレームを読み込んだ時刻です。`MAX_TIME_GAP` の初期値は0.15秒で、実機で両方に現れる変化を見ながら調整します。動画の `received_at` は再生中にPCが読み込んだ時刻です。

ロガーは `READ_INTERVAL`（初期値0.2秒）の待ち時間を挟み、CHごとに `GetCurrentData()` で各ユニットの現在値を読みます。PCに転送済みの波形の最新位置とは別の値です。値が前回と同じでも毎回出力し、保存番号やサンプル位置での重複判定は行いません（Automationマニュアル p.44）。

NR-600の計測ユニット間同期は±1μs以下であり、今回の速報値の照合には現在値を使う方針です（NR-600マニュアル 10-2～10-3）。この仕様はCHを順に読むCOM呼出しの時間差や、カメラとの同期を保証するものではありません。多チャンネルリンクモードではサンプリング周期のずれが40ms以下、NR-CA04と他種ユニットの組み合わせでは設定に応じて最大40msまたは1サンプリング周期になる注記があります。現場の構成とOCRとの実際の時刻差を確認します。

## 取得関数と単体起動

`src/logger.py` の `read_logger(channel_names, stop_requested)` と、`src/counter.py` の `read_counter(source, stop_requested, show_segment_scores=False)` は、データを1件ずつ `yield` する取得関数です。JSONL出力と親の監視は各スクリプトの `main()` に置きます。親の `src/main.py` は引き続き `subprocess` で2つのスクリプトを起動し、取得関数をimportしません。

取得関数は、読み進めたスレッドで機器を開き、停止・解放まで行います。現在は取得子のメインスレッドで実行し、別スレッドでのCOM利用は対象外です。途中で読み取りを終える場合は、単体起動側と同じく `contextlib.closing()` で囲み、必ず閉じます。ジェネレーターの終了処理をGC任せにしません。設定は各スクリプト先頭に残し、汎用の機器クラスや設定クラスは設けません。

## 無更新・異常・終了の扱い

`acquired_mono_ns` は、ロガーではCH読取後、OCRではフレーム受領後の `time.monotonic_ns()` です。同じWindows PCのプロセス間で古さを比較し、親がパイプから読み出した時刻で取得時刻を置き換えません。カメラの露光時刻や装置内の測定時刻ではありません。CSVの列と `time_gap_s` の計算は従来どおりで、時刻差にはUTCの `received_at` を使います。

| 状況 | 親の動作 |
| --- | --- |
| 起動後、最初の新しいデータが来ない | `STARTUP_TIMEOUT`（30秒）を超えたら両方を停止 |
| 稼働後、新しいデータが来ない | `INPUT_TIMEOUT`（1秒）超で通知。OCRは保持値を破棄し、復帰するまで `waiting` とする |
| 無更新・古いデータだけの状態が続く | 最後に採用したデータの取得時刻から `FAILURE_TIMEOUT`（15秒）を超えたら両方を停止 |
| OCRが読取不能、電圧が欠測・範囲外 | 更新は続いているものとして扱い、従来の欠測状態を出力 |
| 子の非ゼロ終了、読取スレッドの例外、不正なJSONや必須項目 | 入力元と原因を通知し、両方を停止。親も非ゼロで終了 |
| 片方の正常EOF、`Ctrl+C` | 両方へ標準入力を閉じて停止を要求し、終了を確認 |
| 親のCSV書込み失敗 | 両方を停止し、保存失敗を通知。正常終了とは扱わない |

`INPUT_TIMEOUT`より古い入力は計算・CSV出力に使いません。ロガーが止まった間はCSV行を補いません。古い入力や停止処理中の残りの出力を保存し切る保証はありません。

親は両方へ停止を要求してから、共通の `STOP_TIMEOUT`（15秒）の期限まで待ちます。期限を超えた子は強制終了し、さらに最大5秒で終了を確認します。停止中も標準出力を読み捨て、出力待ちで子が詰まることを防ぎます。強制終了・終了確認失敗は通常完了にせず、機器の停止未確認として扱います。

ロガーの既存の `Stop()` 後10秒待機は残し、その後に `GetState() == 1` を確認します。通常の停止待機を無更新の異常と誤判定しないよう、`FAILURE_TIMEOUT`・`STOP_TIMEOUT`は各15秒としています。10秒待機の必要性、COM／SDKの所要時間、各期限は実機で確認・調整してください。Python子プロセスの強制終了だけではWAVE LOGGER PROや装置の停止を保証しません。

監視は親のループ内で行います。親自身がOSの入出力などで長時間ブロックした間の監視継続は保証しません。自動再起動、GUI、パス管理、通信方式の置換は今回追加していません。
