## 1. このプログラムは何を作るのか

ChArUco（チャルコ）板は、白黒のチェス盤の模様と、識別用のArUcoマーカーを組み合わせた板です。「マーカー」は、白黒の小さな升目で番号を表した図形だと思ってください。

カメラ校正では、写真に写った模様と、板の上の既知の配置を対応させます。たとえば「板上で横30mm・縦30mmの位置にある角が、写真のどの画素に写ったか」を調べます。この対応をたくさん集めるために、先に正しい板を作ります。[OpenCV公式のChArUcoの説明](https://docs.opencv.org/4.x/df/d4a/tutorial_charuco_detection.html)も、この板の作成と角の検出を説明しています。

このスクリプトの仕事は、板の定義から画像を描き、周囲に白い余白を追加して保存するところまでです。印刷は、保存後に画像ソフトや印刷ソフトで行います。カメラから写真を取得したり、カメラ係数を計算したりする処理は含まれません。

既定設定で作られる画像は、次の寸法です。

| 部分 | 想定する印刷寸法 | 作られる画素数 |
| --- | --- | --- |
| 板の本体 | 横210mm × 縦150mm | 横2100px × 縦1500px |
| 各辺の白い余白 | 10mmずつ | 100pxずつ |
| 余白を含むPNG全体 | 横230mm × 縦170mm | 横2300px × 縦1700px |
| 1マスの一辺 | 30mm | 300px |
| マーカーの一辺 | 18mm | 180px相当 |

「想定する印刷寸法」としたのは、PNGの画素数だけでは印刷される長さが決まらないためです。この点は後で詳しく説明します。

## 5. 設定値の意味を確かめる

共通設定では次の値を定義しています。

```python
BOARD_SQUARES = (7, 5)
SQUARE_MM = 30.0
MARKER_MM = 18.0
```

`=` は、右側の値に左側の名前を付ける代入です。「等しいかを調べる」記号ではありません。

`BOARD_SQUARES` の値 `(7, 5)` は、2個の値を順序付きでまとめたタプルです。横方向が7マス、縦方向が5マスです。7×5はマスの数であって、検出できるチェス盤の内側の角の数ではありません。内側の角の数は、この設定では `(7 - 1) × (5 - 1) = 24` 個になります。

`SQUARE_MM` は1マスの一辺、`MARKER_MM` は1個のマーカーの一辺です。この題材では、両方ともmmを単位として扱っています。OpenCVが名前の `_MM` を解釈するのではなく、作成側・検出側・寸法換算側で単位の約束を揃えています。

`30.0` や `18.0` は小数を扱う浮動小数点数です。値が整数相当でも `.0` を付けると、Pythonでは小数の型になります。

本体には、次の2個の設定もあります。

```python
PIXELS_PER_MM = 10
MARGIN_MM = 10
```

`PIXELS_PER_MM` は、「印刷上の1mmを、画像の何画素で描くか」です。10なら1mm当たり10pxです。`MARGIN_MM` は、板の各辺へ追加する白い余白です。

ここでの `PIXELS_PER_MM` と、計測用の共通設定 `MM_PER_PX = 0.25` は役割が異なります。前者は印刷用の板画像をどれだけ細かく作るか、後者は補正画像の1画素を実物の何mmとして扱うかです。板生成では `MM_PER_PX` を読み込んでいません。

英大文字とアンダースコアの名前は「設定として扱う値」を示す慣習です。Pythonが変更を禁止しているわけではありません。

## 6. `main()` と、実際に実行される順序

```text
def main() -> None:
```

`def` は関数の定義を始めます。関数とは、名前を付けて呼び出せる処理のまとまりです。`main` はこのプログラムの入口として付けた名前です。丸括弧が空なので、呼ぶ側から渡す引数はありません。

`-> None` は「結果の値を呼出元へ返す関数としては使わない」という型注釈です。何もしないという意味ではありません。画像を保存し、説明を表示する仕事をします。

行末の `:` から関数の中身が始まります。その下の、字下げされた行が `main()` の処理です。関数を定義した時点では中身は実行せず、後で `main()` と呼ばれたときに上から順に進みます。

このファイルの流れは次のとおりです。

```text
必要な機能と設定を読み込む
  ↓
mainという関数を定義する
  ↓
ファイル末尾の条件を満たしたらmainを呼ぶ
  ↓
辞書と板を定義 → 本体を描く → 余白を追加 → PNGへ保存 → 寸法を表示
```

## 7. マーカーの辞書と、板の設計図を作る

```python
dictionary = cv.aruco.getPredefinedDictionary(cv.aruco.DICT_4X4_50)
board = cv.aruco.CharucoBoard(BOARD_SQUARES, SQUARE_MM, MARKER_MM, dictionary)
```

右側の関数を呼んで、その戻り値を左側の変数へ入れています。

`cv.aruco` はOpenCV内でArUcoやChArUcoを扱う機能のまとまりです。`getPredefinedDictionary(...)` は、用意されたマーカー辞書を取り出します。`DICT_4X4_50` は、4×4の情報ビットを使う50種類のマーカーを持つ辞書です。板を4×4マスにする設定ではありません。板のマス数は先ほどの `(7, 5)` で決まります。

`dictionary` はPythonの `{...}` 形式の辞書そのものではなく、OpenCVのマーカー辞書オブジェクトです。同じ「辞書」という言葉でも役割が違います。

`CharucoBoard(...)` は、板の配置と寸法を保持するオブジェクトを作ります。オブジェクトは、データと、そのデータに対する操作をひとまとめにしたものです。この段階の `board` は保存用PNGではなく、「このマス数・この寸法・この辞書で構成する板」という設計図に相当します。

生成側と校正側は、同じ辞書・マス数・寸法を使う必要があります。共通設定だけでなく、辞書名も後の校正スクリプトと一致させています。

## 8. mmで表した寸法を、pxの寸法へ変える

```python
board_width_mm = BOARD_SQUARES[0] * SQUARE_MM
board_height_mm = BOARD_SQUARES[1] * SQUARE_MM
board_width_px = int(board_width_mm * PIXELS_PER_MM)
board_height_px = int(board_height_mm * PIXELS_PER_MM)
```

`BOARD_SQUARES[0]` は、タプルの最初の値7です。Pythonでは位置の番号が0から始まるため、`[1]` は2番目の値5です。

`*` は掛け算です。既定値を入れると、途中の変数は次のようになります。

| 計算 | 結果 | 単位 |
| --- | --- | --- |
| `7 * 30.0` | `board_width_mm = 210.0` | mm |
| `5 * 30.0` | `board_height_mm = 150.0` | mm |
| `210.0 * 10` | `2100.0` | px相当 |
| `int(2100.0)` | `board_width_px = 2100` | px |
| `int(150.0 * 10)` | `board_height_px = 1500` | px |

画像サイズには整数を渡すので、`int(...)` で整数へ変換しています。`int` は四捨五入ではありません。正の値に小数部分があれば切り捨てます。現在の設定ではちょうど整数になるため差は出ませんが、寸法や画素密度を細かい小数へ変える場合は、この丸めが生じます。

単位にも注目してください。`mm × (px/mm) = px` なので、実寸から画素数へ変換できます。名前の末尾の `_mm` と `_px` を追うと、どの単位を扱っているか分かります。

## 9. 板の画像を描く

```python
board_image = board.generateImage((board_width_px, board_height_px))
```

`board.generateImage(...)` のように、オブジェクトの後へドットと関数名を付けた操作をメソッドと呼びます。ここでは、設計図 `board` に「指定した画像サイズで板を描いて」と依頼しています。

渡すサイズの順序は **横幅、縦高さ** です。既定値なら `(2100, 1500)` になります。

返ってくる `board_image` はNumPy配列です。配列は、たくさんの数を規則正しく並べて持つ仕組みです。この板はグレースケール画像なので、各画素に明るさの値を1個ずつ持ちます。

| 性質 | 既定設定での値 | 読み方 |
| --- | --- | --- |
| `board_image.shape` | `(1500, 2100)` | 縦1500行、横2100列 |
| `board_image.dtype` | `uint8` | 0〜255の整数で明るさを表す |
| 黒 | `0` | 最も暗い |
| 白 | `255` | 最も明るい |

`generateImage` へ渡すサイズは `(幅, 高さ)`、返された配列の形状は `(高さ, 幅)` です。この順序の違いは画像処理でよく出てくるので、その都度確認します。

## 10. 白い余白を上下左右へ付ける

最初に、余白のmmをpxへ変えます。

```python
margin_px = int(MARGIN_MM * PIXELS_PER_MM)
```

既定値では `10 * 10 = 100` なので、1辺につき100pxです。

続く `cv.copyMakeBorder(...)` は、画像の外側へ縁を足した、新しい画像を返します。実装では引数を縦に並べています。対応関係を表にすると次のとおりです。

| 渡している引数 | 意味 |
| --- | --- |
| `board_image` | 元になる板の画像 |
| 1個目の `margin_px` | 上に足す100px |
| 2個目の `margin_px` | 下に足す100px |
| 3個目の `margin_px` | 左に足す100px |
| 4個目の `margin_px` | 右に足す100px |
| `cv.BORDER_CONSTANT` | 足した部分を一定の値で塗る方式 |
| `value=255` | その値は255、つまり白 |

`value=255` は、引数名を明示して値を渡すキーワード引数です。設定ファイルを書き換えているわけではありません。

戻り値は `printable_image` に入ります。本体の配列は `(1500, 2100)` でしたが、上下左右に100pxずつ追加されるので、こちらの形状は `(1700, 2300)` になります。本体を拡大縮小しているのではなく、外側へ白い領域を追加しています。

丸括弧の内側は複数行に分けて書けます。行末のカンマは引数の区切りで、最後の引数の後のカンマもPythonでは許されます。これは処理を複数回実行する記法ではありません。

## 11. 保存先を作り、共通関数に保存を任せる

```python
output_path = OUTPUT_DIRECTORY / "charuco_board.png"
write_png(output_path, printable_image)
```

`OUTPUT_DIRECTORY` は文字列ではなく、`pathlib.Path` というパスを扱うオブジェクトです。`Path` に対して `/` を使うと、その後ろへファイル名やフォルダ名を連結できます。数値の割り算とは、左側の値の種類が違います。

共通設定の `BASE_DIRECTORY = Path(__file__).resolve().parent` は、`workflow_settings.py` 自身が置かれたフォルダを基準にします。そのため、既定の保存先はPowerShellを開いた場所ではなく `src/output/` です。

`write_png(...)` に渡す2個の引数は「どこへ」「何を」です。中では次の順序で進みます。

1. `check_output_path(path, ".png", [])` で保存先を絶対パスへ直し、拡張子が `.png` であることを確認する。
2. `encode_png(image)` で、配列をPNGのデータへ変換する。
3. `path.parent.mkdir(parents=True, exist_ok=True)` で保存先のフォルダを用意する。
4. `path.write_bytes(png_data)` でPNGのバイト列をファイルへ書く。

`parents=True` は途中の親フォルダも作る指定、`exist_ok=True` はフォルダがすでに存在することをエラーにしない指定です。

`encode_png()` 内では `cv.imencode(".png", image)` を呼びます。画像を画面表示するのではなく、ファイルへ書けるPNG形式のバイト列へ変換します。変換に失敗した場合は `OSError` を発生させます。先に変換してから書込を始めるため、PNG変換が失敗した段階で既存ファイルを書き換えることはありません。ただし、実際の書込中の故障まで含めた完全な保存保証や、バックアップ作成の実装はありません。

この板生成では保護対象の入力ファイルがないので、`check_output_path` の第3引数は空リスト `[]` です。これは「既存の出力を上書きしない」という指定ではありません。

## 12. `print` とf文字列で、結果と印刷寸法を伝える

```python
print(f"保存: {output_path}")
```

`print(...)` はターミナルへ文字を表示します。画像の中へ文字を描く処理ではありません。

文字列の前の `f` は、`{...}` の中へ変数や式を書き、実際の値を埋め込めるf文字列の印です。たとえば `output_path` が保存先の絶対パスなら、そのパスが表示されます。

寸法の表示には次のような部分があります。

```python
f"黒白の板本体: {board_width_mm:g} × {board_height_mm:g}mm、1マス: {SQUARE_MM:g}mm"
```

`{board_width_mm:g}` のコロン以降の `g` は表示形式です。`210.0` を `210` のように見やすく表示します。変数自体を整数へ変えているわけではありません。

全体の寸法の表示では `board_width_mm + 2 * MARGIN_MM` を計算しています。左右に余白を1個ずつ足すので、余白は2倍です。縦も上下で2倍になります。

最後の「印刷後に縦横・1マスの寸法を実測し、平らで硬い板へ貼ってください」という表示は、校正で使う実物の板の条件を伝えています。プログラムが印刷結果を測定した、という報告ではありません。

## 13. PNGの画素密度と、実際の印刷寸法を区別する

この実装はPNGを作りますが、`write_png()` でDPIを指定していません。「1mmを10pxで作った」という数値は画像生成時の計算に使った約束であり、印刷ソフトへ寸法を強制する命令ではありません。

単位を換算すると、10px/mmは次の密度に相当します。

```text
10 px/mm × 25.4 mm/inch = 254 px/inch
```

2300px幅の画像全体を230mm幅で印刷すると、設計どおり1マスが30mmになります。しかし、印刷ソフトが任意に300dpiとして扱ったり、「用紙に合わせる」で縮小したりすると、同じ2300pxの画像でも実寸は変わります。仮に300px/inchで2300pxを置くと、幅は `2300 / 300 * 25.4 ≈ 194.7mm` です。

印刷時には、余白込み全体を横230mm × 縦170mm、または本体を横210mm × 縦150mmとして扱えるようにします。そのうえで、実物の横・縦・1マスを定規などで測ります。「100%」という表示だけでは、印刷ソフトが元の物理寸法をどう解釈したかまでは分かりません。

カメラ校正・後続の寸法補正が参照するのは、`SQUARE_MM = 30.0` などの板の設計値です。実物が設計と違う、縦横の倍率が違う、貼付け面が反る、といった状態をこのコードは自動で検出しません。生成に成功したことと、印刷した板の寸法が正しいことは、別々に確認します。

## 14. ファイル末尾の `if __name__ ...` を読む

```python
if __name__ == "__main__":
    main()
```

`if` は条件分岐です。`==` は左と右が等しいかを調べます。

Pythonがこのファイルを実行の入口として動かすと、特別な変数 `__name__` に `"__main__"` が入ります。その場合だけ、字下げされた `main()` を実行します。

別のPythonコードが部品としてこのファイルを読み込む場合は、この条件は通常成り立ちません。そのため、関数を読み込んだだけで勝手に板PNGを保存しない構造です。「`main` という関数名だから自動実行される」のではなく、この条件の中で明示的に呼んでいることが重要です。

## 15. 失敗したときに何が起こるか

このスクリプトには、例外を捕まえて処理を続ける `try` 文はありません。次のような問題があれば、例外が呼出元へ伝わって実行が止まります。

| 問題 | 起こること・確認する場所 |
| --- | --- |
| OpenCVが入っていない、実行環境が違う | 最初の `import cv2` などで止まる。題材の環境を使って実行する |
| 設定・`utils/` をコピーしていない | 自作モジュールの読込で止まる。必要なファイルを揃える |
| マス数・寸法・画像サイズが不正 | OpenCV側の処理などで止まり得る。正の値と板の構成を確認する |
| PNGへ変換できない | 共通関数が `OSError("PNGを作成できません")` を発生させる |
| 保存フォルダを作れない、書込権限・空き容量がない | フォルダ作成や書込で止まる。保存先を確認する |

設定のすべてを事前に検査する独自処理はありません。エラーで止まった場合、後ろの「保存: ...」や寸法の表示まで到達するとは限りません。最後にメッセージが出たかと、実際のPNGが開けるかを確認します。

## 16. どこを変えると何が変わるか

| 変える値 | 主な結果 | 一緒に確認すること |
| --- | --- | --- |
| `PIXELS_PER_MM` | 画像の画素数とファイル量が変わる | 画素数とmmの約束を保って印刷し、実寸を測る。値を大きくしてもプリンターや撮影の誤差が自動で減るわけではない |
| `MARGIN_MM` | 白い余白とPNG全体の寸法が変わる | 印刷ソフトに指定する全体寸法も変わる |
| `OUTPUT_DIRECTORY` | 板PNGの保存先が変わる | 共通設定なので、ほかの工程の出力先も参照する |
| `BOARD_SQUARES` | マス数・本体寸法・角の配置が変わる | 生成・校正・補正の板定義を揃え、印刷と校正をやり直す |
| `SQUARE_MM` | 1マスの実寸と本体寸法が変わる | 印刷した実物を一致させ、校正をやり直す |
| `MARKER_MM` | マス内のマーカーの大きさが変わる | 1マスより小さい妥当な寸法にし、印刷と校正をやり直す |

辞書名を変える場合も、生成側だけでなく検出する各スクリプトの辞書を揃える必要があります。まずは板の寸法と保存先を理解し、必要な設定だけを変更するのが読みやすい進め方です。

## 17. 手元で確認できることと、この説明の範囲

読み終わったら、次を自分の言葉でたどってみてください。

1. `(7, 5)` と `30.0` から、どの行で210mm × 150mmを求めているか。
2. 本体の `(2100, 1500)` と配列の `(1500, 2100)` は、それぞれ何の順序か。
3. `margin_px` が100になる理由と、全体が2300px × 1700pxになる理由。
4. 画像が保存されるのはどの関数で、印刷を実行するのは誰か。
5. 画面上の寸法表示だけで実物の寸法を確認したことにならない理由。

この文書の作成時には、現行コードを読み、OpenCV 5.0.0の環境で同じ板生成・余白追加をメモリ内で実行しました。本体配列 `(1500, 2100)`、余白込み `(1700, 2300)`、型 `uint8`、内側の角24点を確認しています。同じPNG変換処理の出力には、画素の物理密度を記録する `pHYs` チャンクが含まれていないことも確認しました。これはこの環境・この実装での確認です。

実際のプリンターでの寸法、紙や貼付け面の平面性、印刷した板を使う実カメラの校正精度は、この確認では測定していません。次の[校正スクリプトの解説](00_2_calibrate_camera.md)へ進む前に、実物の板の寸法を確認します。
